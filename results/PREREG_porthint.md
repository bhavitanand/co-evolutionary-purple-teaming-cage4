# Pre-registration: port-hopping Red plus a Blue prompt note that ports are unreliable (written 3-Nov ~20:15, before any run)

Follow-up to results/PREREG_porthop.md (not supported). Same design, plus one sentence added to the Blue prompt: "NOTE: attackers can change the destination port from one round to the next, so a port that appeared in a past attack is not a reliable signal. Prefer rules on process_name, parent_process, privilege, protocol or service_name that would still match if the port changed." Condition `coevo`, variant `porthop+porthint`, ten runs, seeds 35-44 (seeds only fix the environment; all conditions share seeds), 8 rounds, 4B model. One run each, no tuning, one scoring on the test seeds.
Claim "telling Blue the port is unreliable restores robustness to port changes" is supported only if native recall with the test ports re-drawn, minus the 20 original co-evolved runs, has a 95% bootstrap interval above zero and FPR on the original test is no more than 0.02 higher. Otherwise reported as not supported. Caveat: the note is a hint that tells Blue what the test varies, so a positive result would show that Blue can use such information, not that it discovers it.
